# 制度问答 Agent（policy-qa）

把公司制度文档变成一个能问答的服务：员工问一句，答案**每条结论都带条款出处**，制度里没写的明确说没有。

面向的场景：传统企业数字化部门最常做的「内部知识库 + 智能问答」。也是我用来练 FastAPI（后端接口框架）、
uv（Python 环境与依赖管理）、Docker（容器化）、评测（Evaluation）的主项目。

> 语料说明：`corpus/` 里的三份制度是**按常见企业制度编写的演示数据**（每份文档顶部都标注了），
> 不代表任何真实公司。要换成真实制度，只需替换 `corpus/` 目录里的 markdown 文件——
> 一份文档一个文件，条款标题用 `### 第N条 标题`，代码会自动按条款切分并生成出处。

## 数据流

```
                       corpus/*.md
                            │
              ① 条款级切分（app/corpus.py）
                 按 "### 第N条" 切开，每条带《文档》第N条 出处
                            │
                            ▼
                    List[Clause]  58 条
                            │
              ② 组装提示词（app/prompts.py）
                 条款全文 + 员工问题；系统提示词写死三条硬规则
                            │
                            ▼
              ③ 调模型（app/llm.py）
                 超时 / 重试 / 用量统计 都在这一层
                            │
                            ▼
              ④ 出处校验（app/main.py: verify_citations）
                 用正则抽出答案里的《文档》第N条，逐个比对真实条款
                 —— 这一步是纯代码，不信模型自觉
                            │
                            ▼
        { answer, citations[], invalid_citations[], refused, usage, latency_ms }
```

三条硬规则写在 `app/prompts.py` 里：**只用给定条款**、**每条结论必须标出处**、
**条款里没有就说没有**。第四层用代码再验一次出处，两层加起来才敢给员工看。

## 三个接口

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/health` | 服务活着吗、用的哪个模型、加载了多少条款 |
| GET | `/corpus` | 文档清单与条款数（答非所问时先看这里） |
| POST | `/ask` | 提问，返回答案 + 出处 + 用量 + 延迟 |

## 几个设计决定（面试会问的）

### ① 为什么按「条款」切，不按字数切

按字数硬切（比如每 500 字一段）在这类文档上一定出事：一条「第5条 住宿标准」可能被切成两半，
检索回来半条，答案就漏掉条件（比如漏了「含税」）；而且没法说清出处是第几条。

制度文档天生有条款结构，顺着它切，**出处是天然的、不用猜**。
经验：**文档自带的标题结构，比任何切块算法都可靠。**

### ② 为什么出处要用代码验一遍

模型很擅长「顺便」编一个《员工手册》第99条，读起来毫无破绽——这类幻觉对内部知识库是致命的，
员工照着错的条款去报销，锅在公司。

所以 `verify_citations()` 用正则把答案里的引用全抽出来，逐个比对真实条款表。
这一步**不看模型怎么说，只看它有没有引用不存在的东西**，是确定性的字符串比对。

### ③ 为什么允许「拒答」，而且要显式标出来

制度问答里，编一个答案的代价远大于说「没规定」。所以：

- 系统提示词第 3 条要求明确说「现行制度里没有关于……的规定」；
- 接口返回 `refused` 字段，评测时单独统计**该拒答时有没有拒答**（漏拒 = 幻觉风险，错拒 = 可用性差）。

### ④ 为什么 M1 故意用「全量投喂」

先把最短链路跑通，拿到一个**能对比的基线**：58 条条款全塞进去，准确率最高但成本也最高（约 4280 tokens/次）。
M2 上向量检索之后，用同一套题目对比两条路的 通过率 / 幻觉率 / token 成本 / 延迟。

没有基线就没有「优化了多少」可讲——这一步是给后面的对比留证据。

## 已知限制（还没做，别当成已完成）

- **没有向量检索**：现在是全量投喂，条款数一多（比如 500 条）就会顶到成本和延迟上限
- **没有多轮对话**：每次提问独立，追问「那二类城市呢」需要重新说全
- **没有鉴权**：接口谁都能调，只适合内网或演示
- **没有评测集**：现在只有 3 条手工抽查，M3 要补 20 条并算通过率/幻觉率
- **没有 Docker**：M4 补，方便部署到云服务器

## 语料换成你自己的制度

1. 把 PDF/Word 转成 markdown（条款标题保持 `### 第N条 标题` 这一层）
2. 丢进 `corpus/`，重启服务
3. `GET /corpus` 看一眼条款数对不对——切分错了这里立刻能发现
