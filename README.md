# 制度问答 Agent（policy-qa）

把公司制度文档变成一个能问答的服务：员工问一句，答案**每条结论都带条款出处**，制度里没写的明确说没有。

面向的场景：传统企业数字化部门最常做的「内部知识库 + 智能问答」。也是我用来练 FastAPI（后端接口框架）、
uv（Python 环境与依赖管理）、Docker（容器化）、评测（Evaluation）的主项目。

> 语料说明：`corpus/` 里的三份制度是**按常见企业制度编写的演示数据**（每份文档顶部都标注了），
> 不代表任何真实公司。要换成真实制度，只需替换 `corpus/` 目录里的 markdown 文件——
> 一份文档一个文件，条款标题用 `### 第N条 标题`，代码会自动按条款切分并生成出处。

## M2：四种检索方式，21 题实测

评测集 21 条（`eval/cases.json`），覆盖：直接查条款、需要计算、跨文档、同义表达、
以及 3 条**制度里没写**的陷阱题（带宠物、配不配车位、有没有陪护假）。
评分全部是确定性断言（命中条款 / 关键数字 / 有无虚构引用 / 该不该拒答），不用 LLM 裁判——
同一套题要在四种检索方式上对比，评分开销必须为零。

### 结果一：top_k = 8（宽松检索）

| 方式 | 通过 | 通过率 | 平均 tokens | 相对全量投喂 | 平均延迟 |
|---|---|---|---|---|---|
| full（全量投喂，基线） | 21/21 | 100% | **4276** | 100% | 1090ms |
| bm25（关键词） | 21/21 | 100% | **959** | **22.4%** | 993ms |
| vector（向量） | 21/21 | 100% | **964** | 22.5% | 1004ms |
| hybrid（RRF 融合） | 21/21 | 100% | 962 | 22.5% | 1114ms |

**结论要说得诚实：在 58 条条款这个规模下，换检索方式没提升准确率，只把成本降到 22%。**
如果就此收工，很容易得出错误结论「向量检索没用」。所以又做了下面两件事。

### 结果二：只看检索质量（不经过模型）

| 方式 | recall@1 | recall@3 | recall@8 |
|---|---|---|---|
| bm25 | **55.6%** | 88.9% | 100% |
| vector | **83.3%** | 100% | 100% |
| hybrid | 66.7% | 100% | 100% |

差异是真实存在的：**排第一的检索结果，关键词只对了 55.6%，向量对了 83.3%。**
但在 top_k=8 时两者都到 100%，所以答案层面看不出差别——**「多给几条」把检索质量问题盖住了。**

### 结果三：把 top_k 压到 3（条款变多时的现实配置）

条款数上千时不可能还一次喂 8 条。压到 3 条：

| 方式 | 通过 | 通过率 | 平均 tokens |
|---|---|---|---|
| bm25 | 19/21 | **90.5%** | 595 |
| vector | 21/21 | **100%** | 591 |
| hybrid | 21/21 | 100% | 608 |

失败的正是「问法与条款用词错开」的那两条：

| 题 | 关键词检索捞到 | 应该捞到 | 为什么 |
|---|---|---|---|
| 离职时年假没休完，怎么折算成钱 | 《员工手册》第19、20条 + 考勤第16条（折算公式） | 《考勤与请假管理制度》第15条（300% 补偿） | 问句里是「折算成钱」，条款里写的是「未休补偿」 |
| 报销的钱什么时候能打到我卡上 | 《员工手册》第8条 + 报销第17条（不予报销） | 《差旅与费用报销制度》第16条（次月 15 日付款） | 问句是「打到我卡上」，条款里写的是「付款周期」 |

**这就是向量检索真正解决的问题：不是「更先进」，而是「问法和条款用词不一样时还能捞回来」。**

### 一个反直觉的发现：RRF 融合不一定更好

`recall@1`：vector 83.3%，hybrid 只有 66.7%。原因：
RRF（Reciprocal Rank Fusion，基于排名的倒数融合）是**无条件信任两路**，
当其中一路明显更强时，弱的那一路会把结果拉平。

所以下次要改的地方很明确：**给两路加权**（比如 0.3 × bm25 + 0.7 × vector），
或者先按查询类型判路（问数字的走关键词，问同义表达的走向量）。
「加了融合反而变差」这件事，比「融合就是好」可信得多——这也是这一轮最值钱的发现。

## 数据流

```
                       corpus/*.md
                            │
              ① 条款级切分（app/corpus.py）
                 按 "### 第N条" 切开，每条带《文档》第N条 出处
                            │
                            ▼
                    List[Clause]  58 条
                            │
              ② 取条款（app/retrieval.py）—— 四档可切
                 full   58 条全给（基线）
                 bm25   字符二元组 + BM25 打分，纯代码零下载
                 vector Chroma + bge-small-zh 语义向量
                 hybrid 两路 RRF 融合（排名倒数相加）
                            │
                            ▼
              ③ 组装提示词（app/prompts.py）
                 条款全文 + 员工问题；系统提示词写死三条硬规则
                            │
                            ▼
              ④ 调模型（app/llm.py）
                 超时 / 重试 / 用量统计 都在这一层
                            │
                            ▼
              ⑤ 出处校验（app/main.py: verify_citations）
                 用正则抽出答案里的《文档》第N条，逐个比对真实条款
                 —— 这一步是纯代码，不信模型自觉
                            │
                            ▼
        { answer, citations[], invalid_citations[], refused, usage, latency_ms }
```

三条硬规则写在 `app/prompts.py` 里：**只用给定条款**、**每条结论必须标出处**、
**条款里没有就说没有**。第五层用代码再验一次出处，两层加起来才敢给员工看。

`netfix.py` 看着不像业务代码，但它解决「换台机器就跑不起来」：见下面的踩坑记录。

## 几个设计决定（面试会问的）

### ① 为什么按「条款」切，不按字数切

按字数硬切（比如每 500 字一段）在这类文档上一定出事：一条「第5条 住宿标准」可能被切成两半，
检索回来半条，答案就漏掉条件（比如漏了「含税」）；而且没法说清出处是第几条。

制度文档天生有条款结构，顺着它切，**出处是天然的、不用猜**。
经验：**文档自带的标题结构，比任何切块算法都可靠。**

### ② 为什么出处要用代码验一遍

模型很擅长「顺便」编一个《员工手册》第99条，读起来毫无破绽——这类幻觉对内部知识库是致命的，
员工照着错的条款去报销，锅在公司。

所以 `verify_citations()` 用正则把答案里的引用全抽出来，逐个比对真实条款表。
这一步**不看模型怎么说，只看它有没有引用不存在的东西**，是确定性的字符串比对。

### ③ 为什么允许「拒答」，而且要显式标出来

制度问答里，编一个答案的代价远大于说「没规定」。所以：

- 系统提示词第 3 条要求明确说「现行制度里没有关于……的规定」；
- 接口返回 `refused` 字段，评测时单独统计**该拒答时有没有拒答**（漏拒 = 幻觉风险，错拒 = 可用性差）。

### ④ 为什么 M1 故意用「全量投喂」

先把最短链路跑通，拿到一个**能对比的基线**：58 条条款全塞进去，准确率最高但成本也最高（约 4280 tokens/次）。
M2 上向量检索之后，用同一套题目对比两条路的 通过率 / 幻觉率 / token 成本 / 延迟。

没有基线就没有「优化了多少」可讲——这一步是给后面的对比留证据。

## 已知限制（还没做，别当成已完成）

- **语料只有 58 条**：这是最大的短板。检索差距在 top_k=3 才露出来，条款上千时才会成为主要矛盾 → M3 要把语料扩到 10 倍
- **RRF 没有加权**：混合检索的 recall@1 反而低于纯向量，下一步按查询类型判路或加权重
- **没有多轮对话**：每次提问独立，追问「那二类城市呢」需要重新说全
- **没有鉴权**：接口谁都能调，只适合内网或演示
- **拒答只做了粗判断**：`refused` 现在靠关键词粗判（答案里有没有「没有…规定」），M3 要改成「答案是否包含有效引用」这种更硬的口径
- **没有 Docker**：M4 补，方便部署到云服务器

## 这一轮踩到的三个坑（都是真事）

### ① 一下载模型就 `InvalidURL: Invalid port: ':1]'`

现象：模型调用一切正常，唯独 Chroma 下载嵌入模型时报这个错。
根因：环境变量 `NO_PROXY` 里带了**方括号形式的 IPv6** `[::1]`，
HTTP 库按「最后一个冒号后面是端口」解析，于是把 `:1]` 当成了端口号。

修法：`app/netfix.py` 里把 `[::1]`、`::1` 这类条目从 `NO_PROXY` 剔掉。
教训：**报错里的 `':1]'` 这三个字符就是唯一线索**——别转述成「下载模型失败」，
要逐字读它到底在抱怨什么。

### ② 嵌入模型下载超时 → 换源而不是配代理

Chroma 默认要从 S3 下 `all-MiniLM-L6-v2`（还是英文模型，中文效果差）。
这台机器上直连超时；而「配全局代理」会把本来好的连接一起搞坏。

修法：换成 `BAAI/bge-small-zh-v1.5`（中文语义，512 维），
用 `HF_ENDPOINT=https://hf-mirror.com` 走镜像，只在 `netfix.py` 里设这一个变量。
**不要动全局代理**——这是两件不同的事。

### ③ 评测判为失败，其实是我的引用解析写窄了

第一次跑 bm25 是 17/18，失败的那题叫「出差去上海，住宿最多能报多少」，
判它「没命中《差旅与费用报销制度》第5条」。但去看原始答案，模型明明写了
`《差旅与费用报销制度》第4条、第5条` —— 是我的正则只认「每个条号各带书名号」，
把合并写法里的第二个条号丢了。

修法：正则改成先抓书名号 + 后面的一串条号，再把 `第\d+条` 逐个拆出来。

**这条比前两条更重要**：测试报错时，先怀疑自己的工具，再怀疑业务代码。
一上来就改检索逻辑的话，等于把正确的功能改坏。

## 语料换成你自己的制度

1. 把 PDF/Word 转成 markdown（条款标题保持 `### 第N条 标题` 这一层）
2. 丢进 `corpus/`，重启服务
3. `GET /corpus` 看一眼条款数对不对——切分错了这里立刻能发现
